Репозиторий: <https://github.com/Mifort/legacy-real-estate-admin> (ветка `master`).
Исходный проект — `~/projects/testdb.lc`, результат — `~/projects/testII`.

Работа разбита на коммиты по этапам. Первый коммит — импорт исходного legacy-кода; при
очистке истории от секретов из него удалены исходный ключ AES и шифротекст пароля
из дампа, поэтому он совпадает с оригиналом не побайтно. История:

```
Import legacy project testdb.lc as-is
Add Docker environment (php 8.2-apache + mysql 8.0), read DB config from env
Task 1: set admin password via AES_ENCRYPT
Task 2: add NL_MATERIAL and NL_HOUSES dictionaries, link them to NL_PROP_RESALE
Task 3: security audit fixes
Task 4: landing page on Smarty + nadar/quill-delta-parser
Task 5: refresh landing compile dir + updated database dump
Task 6: docs (README, REPORT) and composer-install entrypoint
Enforce LF for infra files via .gitattributes
Security review follow-ups
docs: record independent security re-review results
Rotate exposed credentials and keep secrets out of public sources
Replace Python secrets generator with PHP (runs in php:8.2-cli container)
Store passwords as AES_ENCRYPT(password_hash(...)), key back in config.php
Fix issues from the second independent review (R1–R5)
Delete photo files only after a successful save; reject add with a taken ID
Let the database assign IDs on insert; upload new-record photos as drafts
```

## Как проверялось

Чтобы не выдавать желаемое за проверенное, способ проверки указан явно:

- **браузер** — headless Chrome (образ `ghcr.io/puppeteer/puppeteer`) в той же Docker-сети:
  вход, грид, форма редактирования, сохранение через интерфейс;
- **HTTP** — `curl` к изолированному стенду из чистой копии (свой `.env`, свои порты);
- **по коду** — вывод сделан по чтению кода, вживую не воспроизводилось.

## Окружение (Docker)

- `docker/php/Dockerfile` — `php:8.2-apache`, `mysqli`/`zip`, модули
  `rewrite/include/headers/expires`, `AllowOverride All`, `ServerTokens Prod`, `expose_php=Off`.

- Секреты (пароли MySQL) — в локальном `.env`, который создаёт `scripts/setup-secrets.php`;
  в Git их нет. Порядок запуска — в README.

Проверено (HTTP): установка из чистой копии по README — генератор секретов, сборка,
`composer install`, установка пароля admin, вход, лендинг.

## Задача 1. Пароль пользователю admin

Используется `AES_ENCRYPT`, ключ `AESKEY` задан в `php/config.php` (как в задании;
необязательная переменная `AES_KEY` может его переопределить).

**Как требование совмещено с безопасностью.** `AES_ENCRYPT` обратим, а ключ по условию
лежит в `config.php` — рядом с кодом и дампом. Если шифровать сам пароль, его расшифрует
любой, у кого есть репозиторий. Поэтому шифруется bcrypt-хеш пароля:

```
NL_USER_PASSWORD = AES_ENCRYPT(password_hash(пароль), AESKEY)
```

`password_hash` вычисляется в PHP, `AES_ENCRYPT`/`AES_DECRYPT` выполняет MySQL
(`php/functions.php`: `db_password_sql()`, `db_password_decrypt_sql()`, `password_check()`).
При входе значение расшифровывается и сверяется `password_verify`. Утечка ключа вместе
с дампом раскрывает только bcrypt-хеш. Записи старого формата (`AES_ENCRYPT` от самого
пароля) принимаются при входе и сразу перезаписываются в новом. Ключ и хеши
маскируются в журнале ошибок БД.

Пароль admin задаётся CLI-командой `scripts/set-admin-password.php` из локального
`.local-secrets/admin-password`; в публичном дампе рабочего пароля нет. Ранее
опубликованные учётные данные заменены и удалены из истории Git.

Проверено (HTTP): `AES_DECRYPT` исходным ключом даёт `$2y$…` (60 символов); верный пароль —
вход, неверный — отказ; запись старого формата принимается и переводится в новый;
пользователь, созданный через грид, входит с паролем со спецсимволами; пустой пароль при
редактировании его не меняет; хеш не попадает в ответ грида, ключ — в лог.

## Задача 2. Справочники «Материал дома» и «Тип дома»

`sql/migrations/002_houses_material.sql`:

- `NL_MATERIAL` (`ID_NL_MATERIAL`, `NL_MATERIAL_SHORT`) — по образцу `NL_VIEW`;
- `NL_HOUSES` (`ID_NL_HOUSES`, `NL_HOUSES_SHORT`, `ID_NL_MATERIAL` + FK) — тип дома связан
  с материалом;
- в `NL_PROP_RESALE` добавлены `ID_NL_HOUSES` и `ID_NL_MATERIAL` (индексы + FK);
- тестовые данные: 5 материалов, 5 типов домов, 4 новые квартиры; у каждой квартиры
  материал совпадает с материалом её типа дома.

Материал квартиры хранится отдельно от материала типа дома: так требует задание
(«выбрать Материал дома и Тип дома»). Согласованность пары база не проверяет.

Админка:

- `admin/php/functions.admin.php` — `getMainTableCol` (поля `ID_NL_HOUSES`, `ID_NL_MATERIAL`
  как `select`), `getTableColArray` (наборы полей), `getTableLeftJoins`
  (`NL_HOUSES → NL_MATERIAL`; квартиры → вид, тип, материал, пользователь);
- `admin/parts/dicts.php` — вкладки «Материал дома» и «Тип дома».

Проверено: добавление в справочник (HTTP); в гриде квартир колонки «Тип дома» и
«Материал дома» и форма редактирования со списками (браузер). Полный CRUD справочников
через браузер не проходился.

### Рекомендации (без реализации)

- Для новой системы — только `password_hash`/argon2 без обратимого слоя; prepared statements.
- Обновить jQuery 1.12.4 и jqGrid. Карта в форме квартиры использует Яндекс.Карты без
  API-ключа: в консоли ошибка `Suggest is not available` (legacy, вне рамок задания).
- Поиск по приватному полю сейчас доступен только админу; владельцу — нет.
- HTTPS/HSTS на боевом окружении; не доверять `X-Forwarded-For` без доверенного прокси.

## Задача 4. Лендинг

`index.php` получает данные через `db_query`/`db_fetch_assoc`: дома (`NL_HOUSES` + материал
+ число квартир) и квартиры (`NL_PROP_RESALE` + вид/тип/материал, без контакта
собственника). Описание — Quill Delta (URL-encoded JSON) через `nadar/quill-delta-parser`
(`escapeInput = true`, `javascript:`-ссылки библиотека заменяет на `#`). Вывод — Smarty 5
с `setEscapeHtml(true)`; `nofilter` только у HTML описания. Пути фото ограничены `^/img/...`.

Проверено (HTTP): лендинг отдаёт дома и квартиры, фото отдаются (200), спецсимволы адреса
экранированы; XSS в описании (`<script>`, `javascript:`) нейтрализуется.

## Задача 5. Дамп и репозиторий

`sql/testdb.sql` — итоговый дамп (`mysqldump`, utf8mb4): новые таблицы, связи, тестовые
данные, таблица троттлинга; у admin пустой шифротекст до локальной установки пароля.
Пошаговые изменения — в `sql/migrations/`. Репозиторий опубликован на GitHub
(ссылка в начале); доступ проверяющему выдаёт владелец репозитория.

## Задача 6 и применение ИИ

Работа выполнялась с Claude. Каждое изменение проверялось `php -l`/`node --check` и
вживую — способ проверки указан у каждого пункта. Результат дважды проверялся независимым
аудитом; найденные им дефекты исправлены:

- первая проверка — утечка пароля через README, XSS в `photosFormatter`, поиск по
  приватному полю, HTTP 500 у фото, порча JSON при сохранении, гонка ID и имён файлов;
- вторая проверка подтвердила, что код этих дефектов ещё не исправлен, и указала на
  запись admin в старом формате;
- третья проверка нашла регрессию, внесённую исправлением очистки фото: удаление файлов
  до записи в БД позволяло через `add` с чужим ID удалить фото чужой квартиры (п. 20).

Кроме того, при исправлении найдены дефекты, которых не было в проверках: загрузка фото
в Docker не работала из-за прав на примонтированный каталог; `set_id.php` мог выдавать
устаревший ID из-за кеша INFORMATION_SCHEMA в MySQL 8. Позже резервирование ID через
`set_id.php` заменено назначением ID базой при вставке (п. 17).

Не проверено вживую: пункты с пометкой «по коду», полный CRUD через браузер для всех ролей,
блокировка после 5 неудачных входов.
